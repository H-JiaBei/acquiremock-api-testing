# AcquireMock 支付网关接口自动化测试 · 技术文档

> 面向面试与学习的技术说明文档。对应仓库见 GitHub，被测服务为 [AcquireMock](https://github.com/ashfromsky/acquiremock)（Apache-2.0）。

---

## 一、项目定位

本地部署一个**模拟支付网关**作为被测系统，基于 **Pytest + requests** 搭建分层接口自动化测试，覆盖正常 / 异常 / 边界场景，共 **22 条用例**，并在此过程中发现 **4 处真实缺陷**。

与「测公开玩具 API」的本质区别：被测对象是一个有真实业务逻辑（支付状态机、验签、CSRF、幂等、限流）的本地服务，测试的复杂度与说服力高一个档次。

**技术栈**：Python 3.12 / FastAPI（被测）/ Pytest / requests / pytest-html / SQLite

---

## 二、被测系统：AcquireMock

一个模拟真实支付网关的服务，完整支付链路：

```
创建账单 → 收银台页面 → 卡号支付 → OTP 验证 → Webhook 回调 → 支付完成
```

**支付状态机**：

```
pending → waiting_for_otp → paid
                ├──────────→ failed（卡号非法/余额不足）
                └──────────→ expired（15 分钟未支付）
```

**安全机制**：HMAC-SHA256 签名、CSRF 防护、bcrypt 卡信息存储、限流（5 次/分钟/IP）、账单 15 分钟自动过期。

## 三、部署要点（详见 部署技术文档.md）

```bash
python -m venv .venv
pip install -r requirements.txt
pip install aiosqlite        # 官方 requirements 遗漏，SQLite 模式必需
# .env 配置 DATABASE_URL / WEBHOOK_SECRET / BASE_URL
uvicorn app.main:app --port 8000    # 正确入口是 app.main:app（官方 README 写错）
```

**实测踩坑**（也是排障能力证据）：

| 坑 | 现象 | 根因 |
|---|---|---|
| 启动命令 | `uvicorn main:app` 报错 | 入口实际在 app/ 目录下 |
| 依赖缺失 | SQLite 模式报 `No module named aiosqlite` | requirements 只列了 asyncpg |
| 必填字段 | create-invoice 返回 422 | 官方示例漏了 `redirectUrl` |
| 接口路径 | `/api/transactions` 返回 404 | 文档与实际路由不符 |

## 四、测试框架设计（分层）

```
├── config.py        # 配置层：服务地址、测试常量（卡号、密钥）
├── api_client.py    # 接口封装层：封装接口调用 + HMAC 签名算法
├── conftest.py      # 夹具层：session 客户端、账单 fixture
└── testcases/       # 用例层：按业务模块拆分 5 个测试文件
```

**分层的目的**：接口地址/参数变化时只改配置层与封装层，用例层保持稳定；fixture 复用「创建账单」这个高频前置动作。

## 五、用例设计方法论

按「等价类 / 边界值 / 场景法」设计：

| 接口 | 正常 | 异常 | 边界 |
|---|---|---|---|
| `/health` | 200 + 字段断言 | — | — |
| `/api/create-invoice` | 200 + pageUrl 结构 | 缺 4 个必填字段→422、amount 类型错→422 | **amount=0/-100/10¹⁵** |
| `/checkout/{id}` | 200 HTML | 不存在→404 | — |
| `/api/pay/{id}` | 合法卡→303→OTP | 不存在→404、CSRF 缺失→403、非法卡→402 | — |
| `/webhooks/verify` | 正确签名→valid=true | 缺签名→400、错签名→valid=false | — |

## 六、核心技术点解析（面试重点）

### 1. Webhook HMAC-SHA256 验签

```python
message = json.dumps(payload, sort_keys=True)          # 关键：key 排序保证双方一致
signature = hmac.new(secret.encode(), message.encode(), hashlib.sha256).hexdigest()
# 校验用 hmac.compare_digest()，避免时序攻击（timing attack）
```

**为什么用 HMAC**：接收方用共享密钥重算签名并与请求头里的 `X-Signature` 比对，防止回调被伪造或篡改。测试时我用同一算法生成正确/错误/缺失三种签名，分别断言 `valid=true / false / 400`。

### 2. CSRF 防护

服务端把随机 token 种到 cookie，前端提交时在表单回传，服务端比对 cookie 与表单是否一致。cookie 带 `HttpOnly / Secure / SameSite=Strict` 属性。**关键发现**：该服务的 CSRF 校验排在所有业务校验之前，无 cookie 时直接 403，会掩盖后面的「账单不存在 / 非法卡」分支——这是我在测试中暴露的实现顺序问题。

### 3. 幂等性

通过 `idempotency_key` 请求头：同一 key 的重复支付请求不产生重复交易，直接返回已处理结果。**但实测发现**：create-invoice 接口对 `reference` 没有唯一性约束，重复下单都成功，与「幂等」设计不一致。

### 4. 限流

`/api/pay` 用 slowapi 做 **5 次/分钟/IP** 限流。测试时我注意到：连续重跑测试套件会触发 429，需要等窗口重置——这也是接口测试中「测试本身受被测系统限流影响」的真实场景。

### 5. HTTP 状态码语义

| 状态码 | 含义 | 本项目中的使用 |
|---|---|---|
| 303 | See Other（重定向） | 支付后跳转 OTP/成功页 |
| 400 | 参数错误 | 缺签名 |
| 402 | Payment Required | 余额不足/非法卡 |
| 403 | 禁止 | CSRF 校验失败 |
| 404 | 不存在 | 账单不存在 |
| 410 | Gone | 账单已过期 |
| 422 | 参数校验失败 | 缺必填字段/类型错误 |

### 6. 测试卡号机制

服务端只认一张卡 `4444 4444 4444 4444` 为合法卡（写死在代码里的白名单），其余卡号走「余额不足」分支。这让我能精确构造「合法卡→OTP」和「非法卡→402」两种场景。

## 八、面试高频问答（自测用）

**Q1：为什么选这个项目，而不是测 jsonplaceholder 这种公开 API？**
A：公开 API 没有业务逻辑，只能测「通不通」。AcquireMock 有支付状态机、验签、CSRF、幂等、限流，能测出真实的业务缺陷（金额校验、幂等），说服力强。

**Q2：你的测试框架怎么分层的？为什么？**
A：配置层（config）/ 封装层（api_client）/ 夹具层（conftest）/ 用例层（testcases）。接口变了只改封装层，前置动作复用 fixture，用例只关心「输入→期望」。

**Q3：你发现的最有价值的缺陷是什么？**
A：金额无边界校验——amount=0、负数、10¹⁵ 都返回 200，说明服务端对支付金额没有下限和上限校验，这在真实支付场景是严重的资损风险。我用参数化用例 `[0, -100, 1, 10**15]` 证明了它。

**Q4：Webhook 验签是怎么测的？**
A：读源码确认签名算法是「json 按 key 排序 → HMAC-SHA256 → hexdigest」，在测试里用同一算法生成正确签名断言 `valid=true`，用错误签名断言 `valid=false`，缺失头断言 400。

**Q5：CSRF 是什么？你的接口怎么防护的？**
A：跨站请求伪造。服务端在 checkout 时种 csrf_token cookie，支付时要求表单回传同一 token，比对不一致返回 403。我测试时发现校验顺序问题——它挡在业务校验前面。

**Q6：遇到过什么坑？怎么解决的？**
A：① 官方 README 启动命令写错（main:app → app.main:app）；② requirements 漏 aiosqlite；③ /api/pay 限流导致重跑 429。解决：读源码定位 + 补依赖 + 等限流窗口重置。

**Q7：幂等怎么保证？**
A：通过 idempotency_key 请求头去重。但实测 create-invoice 对 reference 没做唯一性约束，是幂等设计的漏洞。
