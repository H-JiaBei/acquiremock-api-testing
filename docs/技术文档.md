# AcquireMock 支付网关接口自动化测试 · 技术文档

> 本项目以开源支付网关模拟器 [AcquireMock](https://github.com/ashfromsky/acquiremock)（Apache-2.0）为被测对象，基于 Pytest + requests 搭建接口自动化测试。本文档记录项目定位、被测系统、部署方式、测试框架设计与关键测试技术。

## 一、项目概述

- **做什么**：本地部署一个模拟支付网关，为其接口编写自动化测试用例，覆盖正常 / 异常 / 边界场景。
- **成果**：22 条用例全部通过，发现 4 处真实缺陷，输出 HTML 测试报告。
- **技术栈**：Python 3.12 / FastAPI（被测）/ Pytest / requests / pytest-html / SQLite。

## 二、被测系统：AcquireMock

AcquireMock 是一个模拟真实支付网关的服务，完整支付链路：

```
创建账单 → 收银台页面 → 卡号支付 → OTP 验证 → Webhook 回调 → 支付完成
```

**支付状态机**：

```
pending → waiting_for_otp → paid
                ├──────────→ failed（卡号非法/余额不足）
                └──────────→ expired（15 分钟未支付）
```

**安全机制**：HMAC-SHA256 签名、CSRF 防护、bcrypt 卡信息存储、限流（5 次/分钟/IP）、账单 15 分钟自动过期。

## 三、环境与部署

### 环境要求

| 项 | 要求 |
|---|---|
| Python | 3.11+（本机 3.12 实测通过） |
| 数据库 | SQLite（开发）/ PostgreSQL（生产） |
| 依赖 | requirements.txt + aiosqlite |

### 部署步骤

```bash
python -m venv .venv
pip install -r requirements.txt
pip install aiosqlite        # 官方 requirements 遗漏，SQLite 模式必需
# 配置 .env：DATABASE_URL / WEBHOOK_SECRET（≥32 位）/ BASE_URL
uvicorn app.main:app --port 8000    # 正确入口是 app.main:app（官方 README 写错）
```

### 踩坑记录

| 坑 | 现象 | 根因 |
|---|---|---|
| 启动命令 | `uvicorn main:app` 报错 | 入口实际在 app/ 目录下 |
| 依赖缺失 | SQLite 模式报 `No module named aiosqlite` | requirements 只列了 asyncpg |
| 必填字段 | create-invoice 返回 422 | 官方示例漏了 `redirectUrl` |
| 接口路径 | `/api/transactions` 返回 404 | 文档与实际路由不符 |

## 四、被测接口清单

| 接口 | 方法 | 说明 |
|---|---|---|
| `/health` | GET | 健康检查 |
| `/api/create-invoice` | POST | 创建账单（amount / reference / webhookUrl / redirectUrl） |
| `/checkout/{payment_id}` | GET | 收银台页面（种 CSRF cookie） |
| `/api/pay/{payment_id}` | POST | 支付（表单提交，限流 5 次/分钟） |
| `/webhooks/verify` | POST | Webhook 验签 |

> 完整接口以服务启动后的 `/docs`（Swagger）为准。

## 五、测试框架架构

```
├── config.py        # 配置层：服务地址、测试常量（卡号、密钥）
├── api_client.py    # 接口封装层：封装接口调用 + HMAC 签名算法
├── conftest.py      # 夹具层：session 客户端、账单 fixture
└── testcases/       # 用例层：按业务模块拆分 5 个测试文件
```

**分层目的**：接口地址/参数变化时只改配置层与封装层；高频前置动作（创建账单）复用 fixture；用例层只关心「输入 → 期望」。

## 六、用例设计

按「等价类 / 边界值 / 场景法」设计：

| 接口 | 正常 | 异常 | 边界 |
|---|---|---|---|
| `/health` | 200 + 字段断言 | — | — |
| `/api/create-invoice` | 200 + pageUrl 结构 | 缺 4 个必填字段→422、amount 类型错→422 | **amount=0/-100/10¹⁵** |
| `/checkout/{id}` | 200 HTML | 不存在→404 | — |
| `/api/pay/{id}` | 合法卡→303→OTP | 不存在→404、CSRF 缺失→403、非法卡→402 | — |
| `/webhooks/verify` | 正确签名→valid=true | 缺签名→400、错签名→valid=false | — |

## 七、关键测试技术

### 1. Webhook HMAC-SHA256 验签

```python
message = json.dumps(payload, sort_keys=True)   # key 排序保证双方一致
signature = hmac.new(secret.encode(), message.encode(), hashlib.sha256).hexdigest()
# 校验用 hmac.compare_digest()，避免时序攻击
```

接收方用共享密钥重算签名，与请求头 `X-Signature` 比对，防止回调被伪造/篡改。测试时用同一算法生成正确/错误/缺失三种签名，分别断言 `valid=true / false / 400`。

### 2. CSRF 防护

服务端把随机 token 种到 cookie（`HttpOnly / Secure / SameSite=Strict`），前端表单回传，服务端比对是否一致。**关键发现**：该服务 CSRF 校验排在所有业务校验之前，无 cookie 直接 403，会掩盖后面的「账单不存在 / 非法卡」分支。

### 3. 幂等性

通过 `idempotency_key` 请求头去重，同一 key 不产生重复交易。**实测发现**：create-invoice 对 `reference` 无唯一性约束，重复下单都成功，与幂等设计不一致。

### 4. 限流

`/api/pay` 用 slowapi 做 5 次/分钟/IP 限流。测试时注意到：连续重跑测试套件会触发 429，需等窗口重置——这是「测试本身受被测系统限流影响」的真实场景。

### 5. HTTP 状态码语义

| 状态码 | 含义 | 本项目使用 |
|---|---|---|
| 303 | See Other（重定向） | 支付后跳转 OTP/成功页 |
| 400 | 参数错误 | 缺签名 |
| 402 | Payment Required | 余额不足/非法卡 |
| 403 | 禁止 | CSRF 校验失败 |
| 404 | 不存在 | 账单不存在 |
| 410 | Gone | 账单已过期 |
| 422 | 参数校验失败 | 缺必填字段/类型错误 |

### 6. 测试卡号机制

服务端只认 `4444 4444 4444 4444` 为合法卡（代码白名单），其余走「余额不足」分支，从而能精确构造「合法卡→OTP」与「非法卡→402」两种场景。
